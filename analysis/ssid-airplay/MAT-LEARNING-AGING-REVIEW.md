# 固定 IP、MAT 学习与老化复核

## 学习不依赖 DHCP

原 IPv4 发送处理 `0x80052200` 在检查单播、非零源 MAC 和非零源 IP 后，于 `0x800522e0` 调用 MAT 学习 `0x80051c78`；它位于后续 UDP/DHCP 专门处理之前。ARP 路径也在 `0x80051f64` 以 sender MAC/IP 调用同一学习函数。因此 X99 使用固定 IP 并不阻止这些路径更新转换表，不能将“没有 DHCP 就无法学习”作为故障解释。

这只说明代码可达条件，不证明每个实机报文都经过该路径、格式有效或学习一定成功。原指令见 [mat-lookup-learning-disassembly.txt](mat-lookup-learning-disassembly.txt)。

## 查询命中会刷新时间，不直接检查老化

原查询 `0x80051950`：

- 表未初始化或未启用时返回空指针。
- 对普通 IPv4 地址，按四字节 XOR 后取低 6 位查桶，逐节点比较 IP。
- 命中后调用原时钟访问函数 `0x801501dc`，将低 32 位写回节点的 lastTime，并返回该节点 MAC 指针；此命中路径没有比较旧 lastTime。
- 未命中时返回表中默认节点的 MAC 指针，不是必然丢弃或返回空。实际默认 MAC 及其转发效果未由本实验验证。
- IPv4 multicast 走独立的 MAC 构造路径；合成 224.0.0.251 输入得到 01:00:5e:00:00:fb，不据此宣称完整 mDNS 或 AirPlay 流程无问题。

八组原函数实验通过，涵盖未初始化、禁用、近期命中、很旧的命中、空桶、碰撞未命中、碰撞链后续命中及 multicast。使用合成表和时钟对象，原查询及原时钟访问指令均执行。没有修改固件文件或访问 AP。

## 已定位的老化条件位于学习遍历分支

`0x80051c78` 学习时，若遍历节点与当前学习 IP 相同，转入 MAC/时间更新分支；若为其他 IP，则比较 `(lastTime + 0x7530 - now)` 的 32 位有符号结果。0x7530 为 30000 **原生时钟单位**，尚未确立秒数。

六组原条件分支实验确认：近期节点保留、恰好阈值时保留、超过阈值进入删除分支；相同 IP 的节点先进入更新分支；两组时钟回绕附近输入也符合该条件。实验在保留/删除/更新分支入口停止，没有执行释放、重新分配或完整学习。

这里只定位了这条老化路径，不证明全固件不存在其他清理/重置机制，也不证明发生了现场误删。不能据此缩减或取消老化、永久绑定 MAC 或发布修复。

共 14 组证据见 [mat-lookup-aging-experiment.json](mat-lookup-aging-experiment.json)。复现：`python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/emulate_mat_lookup.py`。

## 采集顺序必须避免先改变要观测的状态

HTTP 请求可经过上述查询及发送学习路径，刷新/重学 MAT。因此先 HTTP、后读表的正常基线，不能证明请求前表项已经存在或时间戳持续正确。旧记录仍保留，但不将其提升为未经探测影响的故障证据。

采集已调整为：**读 MAT → 读链路/DMA → HTTP → 再读 MAT → 第二次 HTTP**，共三轮。第一轮的首次 MAT 在本工具发出任何 X99 HTTP 请求前采集。后续轮次已经受到此前探测影响，并非完全被动观察。

摘要增加 X99 映射的 MAC SHA256 指纹及 lastTime 原始整数，不存完整 MAC 或其他终端表项。这能比较本次映射是否变化，不能证明指纹属于 X99 的正确物理 MAC；节点缺少完整元数据时不编造时间戳。
