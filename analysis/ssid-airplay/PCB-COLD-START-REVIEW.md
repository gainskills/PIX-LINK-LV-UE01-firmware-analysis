## 用户新增的故障证据

- X99 设置固定 IP 后，长时间断电再加电仍出现连接问题。
- LV-UE01 的 LAN 状态灯能反映链路/活动。
- 换另一台无线转以太设备后更稳定。

用户已补充确认：在 X99 上手动设置固定 IP；LV-UE01 使用独立电源；照片是当前这台设备。因此 X99 的 DHCP 地址获取不是本次故障的必要条件，也不涉及由 X99 USB 给转换器供电的联动。ARP、地址冲突、PHY 协商、无线关联、MAC/IP 转换与独立电源自身的启动质量仍可能相关。LAN 灯和固定地址不能证明数据路径工作。

替代设备更稳定提高了 LV-UE01 设备/固件路径的排查优先级，但单凭此对照仍不能区分软件缺陷、网口兼容性与供电差异。

## 本轮新增的固件定位

### 主动 PHY down/up 序列

0x80017134..0x800171fc 的代码循环处理 5 个 PHY 编号（不等于 PCB 上有 5 个外露网口），先调用同一 PHY 访问函数并传入寄存器参数 0、值 0x3900，同时输出 link Down 日志。随后调用延时，参数 0x12c；再以值 0x3300 循环并输出 link Up 日志。延时单位尚未确认，不能写成确定毫秒数。

可见直接调用点：

- 0x80003958：位于启动相关路径，有模式/状态条件。
- 0x8014e330：位于另一条状态处理路径，有条件及一次性标志控制。

这说明固件会主动改变 PHY 状态，而不仅是读取 LED/链路状态。它是值得核对的启动时序候选；尚未证明 X99 故障时该调用出现、重复出现或协商异常，也未确认状态路径的所有触发条件。不能据此直接删除重协商操作或增加延时。

### MAC/IP 转换和 ARP

- MAT ARP 接收：0x80051a4c（字符串引用定位）。
- IP→MAC 查找：0x80051950，查表并使用备用条目路径。
- IP/MAC 表初始化：0x80052018，有分配失败及已初始化分支。

静态地址仍依赖这些转发/学习路径。下一步应追踪上游先断后连、X99 先启动时的表初始化、学习和恢复顺序；存在函数不等于已定位缺陷。

证据：cold-start-path-disassembly.txt、cold-start-path-xrefs.json、pcb-cold-start-evidence.json。xref 的 function_candidate 是启发式边界，最终分析以反汇编和调用点为准；0x80017134 应视为主动 PHY 操作帮助函数，不能称为已确认的被动链路中断处理函数。

## 下一步验证重点

1. 固定 IP 为 X99 手动配置，供电为独立 USB 电源，均已确认；后续测试保持这些条件不变。
2. 故障出现时先区分：X99 的普通 IP 通信是否也失败，还是仅 AirPlay 发现/播放异常。只有后者才优先深入组播路径。
3. 对比 AP 完成上游连接后再启动 X99，与两台同时冷启动；同时记录 PHY down/up、实际协商和 ARP/MAT 状态。
4. 故障后仅拔插一次网线，观察是否恢复。这是区分 PHY 重协商/重新学习与单纯 DHCP 的对照，不把恢复直接认作根因证明。
5. 用户需要串口启动日志时，再独立确认排针用途、电平和针序；未确认前不提供猜测接法。

本轮没有修改原固件或当前网页候选。已有网页更新未涉及此 PHY/MAT 代码，不能声称修复 X99 冷启动问题。

## 固定 IP 与独立供电确认后的调用链补充

`apclient_connect_status_update`（0x8014df3c）的日志区分断开、连接中和已连接。断开/已连接分支进入 0x8014de44，后者在 0x8014df30 将 0x80212ca0 置 1。监控循环在 0x8014e324 读取该标志，条件满足时在 0x8014e330 调用 PHY down/up，随后 0x8014e340 清零。

相关配置 ID 已从表项交叉核对：0x011a0100=SYS_WLMODE，0x04f20100=WLN_APCLI_CONFIGED；启动另一分支还读取 0x03160100=WAN_PHY。该路径不以 X99 获取 DHCP 地址为必要条件，固定 IP 不会绕开它。

目前只能确认条件控制与调用关系，不能说每次上游连接必定重置网口，也不能把该机制直接认定为缺陷。下一步证据应包含上游状态时间、PHY down/up 时间、实际协商结果与 X99 普通 IP 通信；不要先更改 DHCP、隐藏 SSID 或发射功率来混淆变量。
