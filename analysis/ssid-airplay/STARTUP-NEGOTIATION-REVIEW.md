# 当前组合固件：启动与协商恢复复核

用户要求检查刚启动/刚刷写后的以太网协商；本轮保留当前固件和连接，仅一次恢复态读取，其余为离线机器码复核。没有主动重启、插拔、PHY/GPIO写入或回退。

## 当前固件中具体可疑的启动/恢复逻辑

1. 通用接口启用函数0x800038b0在0x80003958可调用PHY重连；启动和运行时接口重启都可能进入，不能只称启动调用。中继上游状态监控在0x8014e330也可调用同一函数。首次刷后约74秒采样已经计数2，但现有计数不能确定这两次分别来自哪个调用点，也不知道第二次调用前物理链路是否已建立。
2. 主动重连函数0x80017134会对PHY0–4写BMCR3900（含power-down），固定等待参数300，再写3300（启用/重启协商）。参数300沿线程时钟路径处理，墙钟单位未校准，不能称300毫秒或据此断言延时过短。
3. 函数写完便输出Up并返回，不读取POA/BMSR，不等待自动协商完成。故“Up日志/写事务完成”不等于实际链路恢复。
4. 中继监控存在待处理请求时，即使上游还在连接中也可触发上述PHY操作，随后清请求；这段路径不根据真实link/协商结果决定保留请求或重试。不能将它扩大成整个固件不存在其他恢复机制。

这些代码继承原固件，不是本次网页修改新增。结合启动初期已发生两次调用、之后长时间down但不新增调用，**启动时序和协商恢复缺少结果校验是有具体代码支持的候选机制**，还不是已确认根因。正常原版UI诊断启动也曾计数2且可达，因此“次数2”本身不是故障判据。新UI/认证的运行时影响仍未排除。

## 对实际组合镜像的离线执行核对

直接加载当前组合main（SHA5b8797c…），复用现有模型执行4组原PHY/MDIO代码及3组上游监控状态场景，全部通过。组合版诊断跳板也在原PHY实验中执行。结果确认：模拟link down时仍会写完返回；link up时也执行同一power-down/up序列；监控在断开/连接中/已连接三个状态，只要请求有效均可进入重连并清请求。详见[实验记录](combined-startup-negotiation-experiments.json)。

这是有限模型，printf、线程等待和MDIO完成等为替身，不能复现真实电气协商、完整启动并发或证明竞态。没有根据本轮结论强制10M；恢复样本说明当前X99可以在100M通信。

## 后续改进应验证什么

新增调用链核查：监控在state=0、configured=1、接口重启请求0x802551e0=1时，0x8014e3b4调用0x8014e190。该函数关闭、重新启用接口，经0x80003958间接进入PHY重连；返回后清接口请求，再继续检查独立PHY请求0x80212ca0。后者也为1时，0x8014e330仍可再次重连。这提供了同一轮处理重复power-down/up的具体候选路径；并不证明真实失败启动时两个请求同时为1。

独立执行了实际接口重启函数，记录到caller=0x80003960、parent=0x8014e1e0及PHY0写3900/3300；另通过两组完整监控迭代、两组至接口重启返回处的前缀执行验证分支。静态组合对应0/1/1/2次PHY操作。**完整串联模拟在0x8014e30c出现Unicorn异常，原因未解决，不能称已完整复现重复复位或认定实机CPU异常。** 旧监控模型把0x8014e190作为替身，未覆盖这个间接PHY调用。详见[分段实验与限制](double-relink-experiment.json)。

为补足现场证据，已离线制作[启动调用记录候选](../phy-diagnostic/startup-trace/README.md)，保留前8次调用的来源、接口父调用、操作前POA、上游状态、pending和原始CP0 Count。不是修复；尚未安装。当前运行固件仍是c2948bec…。

优先补足启动两次PHY操作的来源、顺序、系统tick和操作前后的POA，确认是否在已有有线link后因上游连接又被打断。记录POA不清BMSR锁存状态，也不必增加PHY写入。新记录需要独立制品和离线校验，不能宣称当前固件已经保存这些未实现字段。

在取得关联后，再评估减少重复power-down、协调上游就绪时序，以及协商后的有界等待/失败处理。不要直接删除初始化、单纯增加未经校准的延时、强制10M或自动反复复位。当前连接正常，继续由用户长测，异常通知后采样；不为验证猜测立即再次重启AP。
