# 上游状态与主动 PHY 重连控制

本轮仅离线分析原固件，未访问或修改 AP。丢包与播放状态没有固定关系，后续不再用播放/暂停对比代替 PHY 故障证据。

## 实际控制链

| 步骤 | 原固件地址 | 已确认行为 |
| --- | --- | --- |
| 上游连接状态更新 | 0x8014df3c | 已检查的断开/已连接分支进入下一个处理函数；连接中分支更新状态 |
| 状态变化处理 | 0x8014de44 | 调用驱动命令 `iwpriv ra0 set DisConnectAllSta=1`，随后将请求标志 0x80212ca0 置 1 |
| 中继监控循环 | 0x8014e1f8 | 读取模式、上游状态及配置；多条分支汇合到请求标志检查 |
| 请求检查 | 0x8014e324/0x8014e328 | 标志等于 1 时，在 0x8014e330 调用主动 PHY 重连 |
| 完成处理 | 0x8014e340 | 函数返回后清除请求标志；这条路径没有验证 BMSR、POA 或协商成功 |

驱动命令名在 0x80171c48，分发表项 0x801efd40 指向 0x800384a4。该处理函数遍历 75 个表项，按字段筛选后调用 0x8008cf98；详见 disconnect-all-sta-disassembly.txt。这不是主动 PHY 重连函数，不能把同一条状态处理中的两项操作视为同一个网口复位。尚未在此完整仿真无线驱动的下游处理或实际 station 类型。

此前监控分支附近的 0x8014dba4/0x8014dc34 也已展开：它们直接操作 0xb0000060、0xb0000604、0xb0000620/624，以参数为 GPIO 位索引清/置位。因此调用参数 0x1f 在这些函数中是位索引 31，不能解释为 PHY 0–4 的端口掩码。这些引脚在 PCB 上的实际用途尚未测量，不猜测为某个 LED 或复位脚。

## 原机器码控制流实验

`emulate_uplink_monitor.py` 校验已知 main SHA，执行原监控循环两轮，并为配置获取、转换、延时、GPIO 帮助函数、驱动调用和重连提供明确的替身。

最初 17 组断言通过（后续增加 3 组重复状态回调实验，合计 20 组，见 UPLINK-NOTIFICATION-REVIEW.md）：

- 中继模式 12 组：上游状态为断开/连接中/已连接，配置标志为 0/1，重连请求为 0/1。只要请求有效，三个上游状态中都可进入 PHY 重连；请求无效时均不进入。这是固定输入模型，不代表每次真实状态变化必然产生重连。
- 每次重连返回后请求被清零，第二轮不再次重连。模拟返回负数也不影响清零；原生重连函数自身没有定义成功/错误返回值，不能将这个替身的负数解释为真实失败码。
- 两组其他模式（数值 0、2）不进入该重连点，原请求保留；这不是其他模式全部行为的覆盖证明。
- 一组模拟重连期间再次置请求：返回后的清零会覆盖这个再次请求。这只证明布尔标志会合并/覆盖这种人为插入的时序，不证明实际并发发生或必然是缺陷。
- 两组原状态处理函数实验：验证实际构造的驱动参数是 `ra0`、`set`、`DisConnectAllSta=1`；驱动替身分别返回 0、-1，函数随后都将 PHY 重连请求置 1。替身返回值未绑定为驱动实际成功/失败语义。

完整结果为 [uplink-monitor-experiment.json](uplink-monitor-experiment.json)。监控全函数范围实际为 0x8014e1f8..0x8014e3c8；反汇编文件还保留后续相邻函数以辨别边界。模型不是完整固件仿真，未验证硬件电气、真实线程调度或故障时序。

## 对故障排查的意义

该控制链不依赖 X99 的 DHCP 获取或是否播放：上游状态变化能请求对 PHY 的主动操作，且这条路径将“写入序列返回”当作请求已处理，没有等待真实 link 恢复。它是具体的候选关联链，但**还没有故障时的调用计数、BMCR/BMSR 或完整时间关联，不能据此认定根因、删除重连或刷入补丁**。

现有诊断候选保留原行为，能记录已定位重连入口调用次数并查询 PHY 控制/状态；未确认实机启动和恢复入口之前继续保留 NOT-FOR-FLASHING。当前能完成的是代码路径与离线行为核查；故障现场的内部 PHY 状态仍是下一项关键证据。

复现：`python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/emulate_uplink_monitor.py`。使用本机已有 Unicorn，当前环境需要在沙箱外初始化仿真库；脚本没有 AP 网络操作。
