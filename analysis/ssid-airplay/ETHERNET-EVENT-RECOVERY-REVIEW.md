# 实际端口事件的恢复分支与查询限制

本轮继续区分三个层次：PHY down/up 操作日志、硬件 link 边沿、网络接口状态事件。它们不能互相替代。

## 六组原事件分支实验

原固件 0x80016ef0 的中断处理读取 POA，比较保存的 link mask，并在变化时投递事件 0x20。随后 0x8000494c 的事件线程进入 0x80004c8c 分支。

`emulate_ethernet_event.py` 执行原分支及原查询包装函数，替代定时器和底层 ioctl，验证六组输入：

- 计数器低于 8 时，增加计数并延迟再次投递 0x20，没有在这次分支查询接口。
- 达到 8 时，取消该延迟事件，计数置 6，再调用 0x80003b68。
- 包装函数发出 ioctl 0xc0306982，接口名指针为 0x8025e740。读取的是该接口的 carrier 值，未在这个分支逐个读取 BMCR/BMSR。
- 保存值 0→查询值 1 时生成事件位 0x204；1→0 时生成 0x208；0→0 或 1→1 保留 0x20。本实验停在重新进入通用事件分发前，没有执行后续网络服务重配置。

六组通过，见 ethernet-event-experiment.json；范围见 ethernet-event-full-disassembly.txt、ethernet-link-query-disassembly.txt。调度参数的墙钟单位未确认，不能将计数解释为确定秒数。

驱动内 ioctl 处理已定位：有线分支 0x80016114 使用 POA 与接口端口掩码；无线分支 0x800ca880 根据接口名和内部 station 状态给出结果。**本轮没有成功取得运行时接口名，不能断言这台中继当前走哪一个分支。** 也不能据此声称已经证明存在逐端口自动修复或缺失全部恢复处理。

## RAM 状态查询已拒收并停用

为确认上述接口，曾对已定位的 RAM 地址发起一次 `reg r 8025e740`。响应地址为 0xb025e740，工具发现不符后立即拒收、退出并关闭连接；未接受任何运行时字段，未继续剩余查询，也没有写命令。

复核原命令 0x80112960 后发现：其读分支在 0x80112a10..0x80112a20 计算 `(input & 0x0ffffffc) | 0xb0000000`，始终映射到硬件寄存器区。写分支也有对应转换。因此，该命令不能用于 RAM 查询或注入诊断代码。一次能返回数据不证明被错误映射的硬件地址有意义或适合重复读取；临时查询脚本已停用，不尝试其他 RAM 地址。此次查询前漏核地址转换属于本轮方法错误，不归因给 AP。

公开失败摘要见 runtime-state-query-rejected.json，原响应仅保留在权限受限的采集目录。未把该结果混入 PHY、上游状态或恢复结论。

## 实际剩余缺口

已知链路变化会进入有延迟的接口状态处理，但仍需故障时的 PHY BMCR/BMSR、主动重连调用记录，以及运行时查询接口才能区分协商失败、重复主动操作和 link up 后的转发故障。原终端的寄存器命令不提供这些 RAM 查询能力，原固件也没有已验证的 PHY 状态命令。

诊断候选仍未实机启动；完整备份不代替恢复入口验证。当前没有依据安全地刷入候选或改变 PHY 参数。本轮实际设备操作只有登录/菜单导航和上述一个被拒收的只读查询；没有重启、修改配置、写寄存器或刷写。
