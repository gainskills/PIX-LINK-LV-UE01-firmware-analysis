# X99 冷启动对照采集

已确认 X99 为手动固定地址 192.168.1.4，LV-UE01 独立供电，照片为当前硬件。当前阶段不修改配置或固件。

## 工具与边界

`collect_cold_start.py` 每次采两轮 AP 状态和 X99 HTTP，发送 3 个 ICMP Echo，并只读取这两个目标的本机 ARP 条目；所有子进程都有超时并等待退出。不调用扫描、配置导出、认证修改、POST、重启、寄存器写入或升级，不保存 HTTP 正文和密码。

工具不要求任何额外 Python 包；使用系统 curl/ping/arp。curl 明确禁用 curlrc、代理及凭据，不跟随重定向。需要主机允许对 LAN 的访问和 ICMP/ARP 权限。结果保存在 cold-start-captures，文件权限 0600。

## 已执行的基线

`cold-start-captures/20261019T225115Z-baseline.json`：

- AP 192.168.1.2:8080 与 X99 192.168.1.4 的两轮 HTTP 均返回 200。
- AP 设备 MAC 匹配，固件 v28K.RPT.20220716；信道 9；运行时间从 8675 增至 8677 秒。
- 原状态页未给出可解析的上游连接状态，记录为 null，不能按管理可达推断 Connected。
- ICMP 三次均无回复，但 HTTP 同时正常；与该环境此前限制一致，不能将此作为设备 100% 丢包结论。
- 本机 ARP 对两个地址均没有条目；本机采集能力/实际路由仍有限，不能把它认作 AP 的 MAT 表为空。
- 没有复现、修复或排除冷启动故障；一次基线不代表长期稳定。

## 用户触发时序

### 2026-10-20 冷启动故障现场（新西兰时间）

用户冷启动后先报告播放卡顿，随后报告问题出现；参考无线转以太设备没有同样的卡顿。播放源及故障最终是否完全停止播放尚待确认。

- `20261019T230421Z-failure.json`：冷启动后 uptime 237–238 秒，AP 和 X99 HTTP 均为 200，信道 9。
- `20261019T230855Z-stutter-http.json`：UTC 23:08:37–23:08:55，12 对低频 GET 中 AP 12/12 返回 200，中位耗时 29.5 ms，最大 37.3 ms；X99 0/12 成功，先出现连接超时，随后为连接失败。AP uptime 498–516 秒持续增加。
- `20261019T230919Z-failure.json`：用户报告问题出现后补采；AP 两轮 HTTP 200、uptime 531–534 秒、信道 9；X99 两轮均连接超时。ICMP 出现 Host is down，但不将 ICMP 当作独立丢包测量。
- `20261019T230359Z-failure.json` 是沙箱内受限探测，ICMP 明示 Operation not permitted；排除该文件作为设备故障证据。随后已在获准的沙箱外重新采集。

目前支持的判断：故障期间 AP 管理面仍可达且未观察到再次重启，而此前可访问的 X99 TCP/80 不再可达。因此不能仅按 AirPlay 发现问题处理。尚不能在以太网 PHY/协商、转发/MAT、上游链路的客户端转发、X99 自身网络栈之间确定根因，也没有音频流抓包或重传计数。

Telnet 可以登录，初始提示符为 CMD>，进入 os 后为 OS>。尝试 `iwpriv ra0 show matinfo` 返回 Unknown Command，未取得 MAT 表。该次终端输出还包含三条 `arp: <pointer> is using my IP address 0.0.0.0!`，其中十六进制值不能认作有效 MAC；这不证明 X99 的 192.168.1.4 冲突，也未定位发出该报文的接口。后一轮帮助查询保存于 `20261019T230959Z-cli.json`。所有连接均已结束，无持续监控。

下一项单变量对照：保留电源、固定 IP、Wi-Fi 和播放源，仅重新插拔一次 X99 与 AP 之间的网线，然后采集 recovered 并核对播放是否恢复。即使恢复，也只能说明链路重新建立及相关表项变化与恢复有关，不能单独证明自动协商错误。

用户随后已重新插拔网线。`20261019T231441Z-recovered.json` 为该操作后的采集，文件标签 recovered 仅表示采集阶段，并不代表实际恢复：AP 两轮 HTTP 200，uptime 852–856 秒、信道 9；X99 两轮 TCP/80 仍连接超时。第一轮 AP 页面耗时 1.054 秒，第二轮 0.017 秒，不能由这两个点推断持续延迟。未观察到 AP 重启，也未观察到单次重新建立以太网链路后 X99 的 HTTP 恢复。用户侧播放状态尚待确认。该结果不能单独证明或排除 PHY、MAT 或 X99 网络栈问题。

用户进一步明确确认：重新插拔网线没有解决问题。

获准在沙箱外读取路由：AP 与 X99 均经 en0，AP 的主机记录没有 REJECT，X99 的主机记录带 REJECT。随后限时抓取 `arp and (host 192.168.1.2 or host 192.168.1.4)`，结果保存于 `20261019T231541Z-arp.json`。本机 192.168.1.12 连续发出四条针对 192.168.1.4 的 ARP who-has，在该约五秒窗口内未捕获对应回复；同时 AP HTTP 仍为 200，X99 的两次连接均超时。抓取进程退出，内核报告零丢弃，不包含音频或应用正文。

这是上游侧地址解析未完成的直接证据，比单独 ICMP 无回应更具体；不能证明请求是否到达 X99 的以太网接口、X99 是否发出回复、或回复是否被 LV-UE01 的 MAT/转发路径丢弃。下一步优先对照只重启 LV-UE01、保持 X99 通电后的行为，并继续离线定位 ARP/MAT 初始化与接收转发路径；在取得下游观测前不宣称已确定驱动根因。

### AP 重启与 X99 自动待机这一混杂因素

用户确认已重启 AP，并说明 X99 曾因长时间不连通进入待机，随后关闭自动待机。之前各失败样本与 X99 进入待机的精确先后关系未知。因此，之前的 ARP 无回复、HTTP 不可达仍是有效的上游观测，但不能单独归因于 AP 丢包；部分失败样本可能属于 X99 待机阶段。用户此前报告的初始播放卡顿与参考设备正常这一对照仍需保留，不能因待机因素直接否定。

`20261019T232257Z-recovered.json`：AP uptime 257–259 秒，确认经历重启；AP 与 X99 两轮 HTTP 均返回 200，X99 总耗时分别 179 ms、21 ms；信道仍为 9。当前普通 TCP/HTTP 可达，但没有验证持续播放。此次同时发生 AP 重启和 X99 待机设置/状态变化，不能将恢复单独归功于 AP 重启，也不能宣称根因或修复成立。下一次故障采集应确认 X99 保持开机、自动待机关闭，先捕获播放卡顿初期，再观察是否发展为普通网络不通。

1. 保留当前固定 IP、独立电源和所有无线配置，按平时出现问题的方式冷启动，不同时更改其他条件。
2. 故障出现时暂时保留状态，不先拔网线、重启或改设置，先执行 failure 采集。
3. failure 记录完成后，再只拔插一次 X99 网线；若恢复，执行 recovered 采集。
4. 对照上游侧 AP/X99 HTTP、AP uptime/信道、以及后续可取得的内部 PHY/MAT 状态。HTTP 正常而只有 AirPlay 异常时，才转向区分发现与音频流。

```sh
python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/collect_cold_start.py --label failure --x99-ip 192.168.1.4
python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/collect_cold_start.py --label recovered --x99-ip 192.168.1.4
```

当前采集不是 X99 网线侧抓包，不会看到全部单播音频；ARP 中出现相同 MAC 也可能是中继转换行为，不能单独视为 IP 冲突。

## AP 内部状态入口的离线进度

在 0x801ef9f0 定位到 matinfo → 0x800402dc；它调用 0x80051728、0x80052744、0x800524e0、0x80053c5c，传入 -1 并输出表信息。邻近命令表还含 stat_reset，说明不能将所有 show 类调试命令都当作无副作用。尚未在 AP 执行 matinfo；先核对其分发语法、函数范围和输出通道，再纳入下一版只读采集。当前工具不声称已取得 AP 内部 PHY 协商、错误计数或 MAT 表。
