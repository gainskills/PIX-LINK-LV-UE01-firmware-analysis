# 原生 PHY 重连的完成判据复核

本轮仅运行本机原固件机器码的离线实验，没有连接 AP、改配置、重启或生成新固件。用户已明确丢包与是否播放没有固定关系；本项不以播放、暂停、待机状态为诊断前提。

## 确认的行为

原固件 `0x80017134..0x80017200` 依次对 PHY 0–4 的寄存器 0 写入 `0x3900`，延时参数为 `0x12c`，然后写入 `0x3300`。每次写之后打印 Down/Up。其完整函数中没有调用原生 PHY 读函数、读取 POA、检查 BMSR/协商完成或执行写后回读。延时单位尚未确认。

因此，**这个帮助函数打印的 `link Up` 只表示代码执行到了开启/重启协商写入之后，不能证明物理链路已建立。** 此结论只针对该函数，不否定独立的端口状态寄存器或链路边沿事件证据。此前 POA 确认的 down/up 仍是独立证据。

原生写函数 `0x800159e0..0x80015a88` 在关闭中断后向 PCR0 发写命令；`0x80015a44..0x80015a50` 循环等待 PCR1 的 bit 0。该循环没有计数、超时分支或休眠；恢复引脚和中断的指令位于循环之后。它没有给调用者提供经过校验的协商成功结果。

上游状态监控在 `0x8014e330` 调用重连函数，并在返回后于 `0x8014e340` 清除请求标志 `0x80212ca0`；该调用点没有先验证链路是否恢复。这不证明整个固件没有其他链路处理，也不证明该标志丢失或具体故障发生。

## 四组实验

`emulate_native_relink.py` 校验原 main SHA 后，原样执行重连和 MDIO 写函数的机器码。只替代 printf、延时和硬件 MMIO，不打补丁、不访问网络。

| 模拟条件 | 观察 |
| --- | --- |
| POA 保持 down，写事务立即完成 | 10 次 PHY 写、5 条 Down、5 条 Up，正常返回；未读 POA，未发 MDIO read |
| POA 保持 up，写事务立即完成 | 写入、日志及延时参数与上一组完全相同 |
| POA 保持 down，每次延迟 20 次轮询后完成 | 仍执行相同写入和 Up 日志；延迟的是事务完成，不是链路协商 |
| 控制器永不报告完成 | 达到仿真器 100,000 指令上限仍停留原等待循环，中断关闭；原函数自身没有此指令上限 |

四组断言通过。机器可读结果为 [native-relink-experiment.json](native-relink-experiment.json)。原始函数反汇编见 `cold-start-path-disassembly.txt`，写函数指令以已知 SHA 的原 main 为准。

## 与现场故障的关系

这是可复现的代码行为，**不是 X99 根因或修复验证**。真实 PHY 电气行为、自动协商时序、MDIO 完成位语义均没有在仿真中验证。故障期间 AP 管理仍常保持可达，不支持直接把全局关中断死循环认定为这些现场故障的原因。

后续诊断必须区分：主动重连函数是否被调用、PHY 是否仍处于 power-down、协商是否完成、实际 link 是否 up，以及 link up 后数据转发是否恢复。现有候选的调用计数和 PHY BMCR/BMSR 查询可补充其中部分证据，但候选仍未实机启动，恢复入口也未验证。本轮不据此删除重连、改协商常量或刷写。

复现命令：`python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/emulate_native_relink.py`。依赖本机已有 Unicorn；在当前 macOS 沙箱中，库初始化 CPU 缓存信息会 SIGILL，沙箱外离线运行四组通过。此工具不具备 AP 网络操作。
