# 以太网速率相关路径与已有状态采样

本轮仅处理本地原固件和既有采集文件，没有连接或修改 AP。

## 原生 MDIO 直接调用范围

对原 main 文件 `0..0x163000` 按指令字扫描 J/JAL，发现 32 个目标为原生 MDIO 读 `0x8001593c` 或写 `0x800159e0` 的引用。全部位于已审查的初始化 `0x80015a88..0x80015c98` 和主动重连 `0x80017134..0x80017210` 范围。其中 31 个是 JAL，另一个是初始化末尾 `0x80015c90` 的尾跳转 J，不能遗漏它。

这不是完整控制流证明：间接调用、其他 MDIO 实现或直接操作硬件寄存器不在该项保证范围内。

镜像含 `long_loop_thread`、`port#%d switch to 10M setting`、`port#%d switch to 100M normal setting` 字符串，但本轮没有发现指向这些字符串的对齐绝对地址指针，也没有定位出执行这些日志的线程。缺失这种引用不能证明死代码；目前不能根据字符串声称存在运行中的速率切换补偿线程，更不能以此提出删除或禁用补丁。

## 历史 POA 采样补充解读

从既有、经过脱敏的 CLI output 严格提取 `Address = 0xb0110080, Value = ...`，得到 48 份有效读数，其中 29 份 port 0 link up，19 份 link down。没有重新访问设备。

本地已保存的 OpenWrt `esw_rt3050.c` 对内部端口使用 POA bit 0 表示 10/100M、bit 9 表示双工、bit 16 表示流控状态，bit 25 表示 link。按该参考解读，29 份 up 样本全部为 **100Mbps、全双工、流控状态位为 1**。down 样本不解释速率/双工位，避免将残留值当成已协商状态。

**这些速率/双工/流控位尚未用匹配的 MT7628KN SDK 或本机原生解码交叉确认**；link 位此前已经由本机原始指令确认。故这是参考解读，不能提升为已测得双方协商一致。原始数据仍支持已确认的 link down/up 事实。

点采样不能排除样本间的短暂重新协商、速率变化或对端双工不一致。流控位也不是 PAUSE 帧计数，不能据此认定流控导致丢包或已排除流控问题。现有证据没有支持直接强制 100M/全双工、修改私有 PHY 常量或关闭流控的具体修复。

## 证据与复现

见 [speed-path-audit.json](speed-path-audit.json)；报告保留每个直接调用地址、每份采集文件名和 POA 值，不含配置或凭据。原固件及参考源文件 SHA256 记录在报告内。

运行 `python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/audit_speed_paths.py`。脚本只读原 main、历史 CLI JSON 与已缓存参考代码，更新分析 JSON，不使用网络、不执行硬件读写。
