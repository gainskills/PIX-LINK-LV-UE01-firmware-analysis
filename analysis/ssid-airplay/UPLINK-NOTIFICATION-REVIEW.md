# 上游通知来源与重复触发边界

本轮继续离线追踪状态回调 0x8014df3c 的调用者，未访问 AP、发送 EAPOL 报文、修改配置或固件。

## 新确认的范围

直接 J/JAL 引用扫描并逐处解码，找到四个调用点：

| 调用点 | 状态参数 | 上下文 |
| --- | --- | --- |
| 0x8004a690 | 0 | 断开处理的尾调用 |
| 0x8004ab20 | 2 | 关联建立路径 |
| 0x8004b1e0 | 1 | 同一关联处理中的连接中分支 |
| 0x8008eb38 | 2 | 0x8008e800 的 PeerPairMsg3Action 路径，前有长度、计数器/MIC、nonce 等校验调用/比较 |

因此，状态通知既有链路处理来源，也有配对握手来源；不能简单把“已连接通知”理解成只有物理连接刚建立时的一次边沿。当前扫描没有找到直接的周期定时器调用，但未穷尽所有间接调用或动态状态变化，不能据此证明稳定连接不会重复通知。

## 回调自身不去重，协议调用者另有过滤

新增三组原始状态回调实验：初始状态分别为 0、1、2，连续注入两次相同状态，并在中间模拟消费者清除请求。两次 0 或两次 2 都会各发一次 DisConnectAllSta 命令、置一次 PHY 请求；两次 1 都不置该请求。原回调没有比较新旧状态再决定是否通知。此前监控/处理实验现合计 20 组通过，结果见 uplink-monitor-experiment.json。

这个结果只证明“如果重复通知到达回调，就可能重复请求”，不是稳定连接实际存在重复通知的证明。

进一步追到配对消息 3 的 0x8008d550 计数器分支。8 组执行原比较器与分支的实验确认：收到值大于已存值时通过这项检查，相同或更旧的非零值被拒绝；收到值为零时存在单独通过分支。后者仅是计数器子检查，后续还有其他校验，**不是整帧接受、重放漏洞或重连触发的证明**。

这意味着，不能把相同非零计数器的报文重传直接推导成反复 PHY 重连。也未模拟完整 WPA 状态机，不能宣称全部重传、换钥或重关联行为已确认。实验见 replay-gate-experiment.json；脚本 emulate_replay_gate.py 不访问网络。

## 当前判断

已缩小为一条需要现场确认的链：有效的上游关联/配对握手通知 → 状态处理 → PHY 重连请求 → 无物理链路恢复检查的 down/up 序列。它不依赖 X99 是否播放或使用 DHCP，但仍缺故障时这条链实际被执行的证据。

尚无依据直接删除通知、增加回调去重、禁用握手重连、修改协商常量或刷入候选。需要先区分实际情况是重复调用、单次重连后的协商失败，还是 link up 后的转发异常。仅凭离线分支可达性无法完成这个区分。

复核命令：

```sh
python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/emulate_uplink_monitor.py
python3 firmware-analysis/ap-192.168.1.2/ssid-airplay/emulate_replay_gate.py
```

当前主机的 Unicorn 初始化需在沙箱外运行。证据均来自已知 SHA 原 main；协议校验实验只执行计数器子分支，不包含真实密码学、真实线程或硬件行为。
