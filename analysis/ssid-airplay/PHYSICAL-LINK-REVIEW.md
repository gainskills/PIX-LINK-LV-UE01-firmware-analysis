# 网口灯全灭时的物理链路证据

2026-10-20，用户确认 LV-UE01 以太网灯完全熄灭，现象与原故障相似。20 MHz 试验后出现；此时没有足够证据判断带宽值本身与故障的因果关系，配置提交/重启可能是触发条件之一。不要把本轮当作 20 MHz 已改善稳定性，也不要仅以无线驱动 PER 解释全灭。

## 只读查询依据

原固件 0x80112960 为 reg 命令。两个参数分支在 0x80112a28 进行一次 lw，随后打印地址和值；三个参数分支另有 sw 写路径。本轮仅允许准确列出的 `reg r` 命令，不提供任意写入。

原固件 0x80016114..0x8001612c 读取 0xb0110080，右移 25 位并与端口掩码比较，交叉验证了本机对该状态寄存器的用途。源代码参照 [OpenWrt esw_rt3050.c](https://raw.githubusercontent.com/openwrt/openwrt/main/target/linux/ramips/files/drivers/net/ethernet/ralink/esw_rt3050.c)：POA=0x80、LINK_S=25、内部 PHY link mask=0x1f；POC0=0x90、DIS_PORT_S=23、DIS_PORT_M=0x7f；P0LED=0xa4、模式 5 为 LINKACT。OpenWrt 只用作寄存器交叉参考，本机固件不是 OpenWrt。

## 现场读数

| 文件（cold-start-captures 下） | 状态寄存器 | 读数 | 解码 |

| 20261020T000410Z-cli.json | POA 0xb0110080 | 0x81818301 | (value >> 25) & 0x1f = 0 |
| 20261020T001840Z-cli.json | POA 0xb0110080 | 0x81808100 | 同样为 0 |
| 同上 | POC0 0xb0110090 | 0x10007f7f | 端口禁用掩码 0x20，仅 bit 5 |
| 同上 | P0LED 0xb01100a4 | 5 | link/activity 模式 |

两个窗口均未看到内部 PHY 0–4 建链。POC0 的端口禁用位没有关闭这些内部端口；P0 LED 也不是强制熄灭模式。PCB 外露 RJ45 具体接哪个 PHY 尚未独立测量，但这里所有五个内部 PHY 的 link 位均为零。寄存器不是 BMCR，不能据此排除单个 PHY 的 power-down 设置。

第二轮命令输出含 Unknown Command，实际只收到一份 POA、POC0、P0LED 读数；不可声称同一轮收到了两份 POA。两个不同文件中的 POA 读数仍各自有效。没有写寄存器、复位 PHY、改配置或重启。所有采集连接均结束。

## 判断与后续范围

这使排查重点转到物理链路建立/恢复，而不是只查 mDNS、IP 地址或 MAT。ARP 无回复可以是无物理链路的后果，但不能倒推出先前所有卡顿都由同一原因造成。PHY 协商、PHY power-down、对端 X99 是否仍开机/网口活跃、线缆/接触、启动时序仍需区分。

先确认 X99 当下开机且网线插紧，保留现场。原固件确有 0x80017134 的 PHY down/up 操作，以及上游状态处理到该函数的条件调用链，见 PCB-COLD-START-REVIEW.md；尚未取得故障当时的调用日志，也没有读取当前 PHY BMCR/BMSR，因此不直接判定该函数漏恢复或删除它。若需 MDIO 查询，应独立检查读事务的实现；不能把向 MDIO 控制器发查询与向 PHY 配置寄存器写值混淆，更不能盲写测试。

20 MHz 配置仍保留，未擅自执行回滚或进一步设置；此次只读检查与配置改变分开记录。

## 新一轮手动重启后的卡顿：捕获到 link down 边沿

用户随后明确：为复现再次重启 AP 和 X99，当前开始卡顿。不能沿用上一轮物理链路始终 down 的静态状态。

`20261020T003305Z-cli.json` 在只读统计/状态查询期间保留到异步日志：`ifra305x: link change. link=00, change=01`。该行碰巧接在统计输出尾部，仍为完整可识别日志；同次查询没有收到可解析的 POA 值。

原固件 0x80016f64 读取 POA；0x80016f6c 将其右移 25 位，0x80016f70 限制为 0x3f；0x80016f74 将当前掩码与保存的旧掩码异或作为 change；0x80016f88 使用格式串 `ifra305x: link change. link=%02x, change=%02x`。因此当前 00、变化 01 对应上次掩码 01，明确为端口 0 从 up 变 down，并非仅从应用超时推断。`link-change-handler-disassembly.txt` 保存解码依据。

随后 `20261020T003433Z-cli.json` 收到三份有效 POA，均为 0x83818301，内部 PHY link mask 为 1，即端口 0 恢复 up。命令列表请求四次，输出只有三次，不能把请求数当成功采样数。

同轮 `20261020T003258Z-arp.json` 中 X99 HTTP 先超时后 200，并捕获以 .4 为 sender 的 ARP；稍后的 `20261020T003336Z-failure.json` 两轮 AP/X99 HTTP 均为 200，AP uptime 251–253 秒，与用户人工重启相符。由此观察到本轮间歇性连通与真实物理掉线/恢复，不能称为持续断链。20 MHz 未消除用户报告的卡顿。

本次无线统计 Tx success=4731，Tx fail=906，Rx success=33668，Rx CRC=13498，RSSI=-25/-30/0；属本次启动的累计值，不与上次启动相减，也不把它单独认定为物理 link down 的原因。

下一项只读观察限定约 35 秒，保留硬件链路变化以及 `[ra305x_relink]====> phy id:N link Down/Up` 日志，以检验是否伴随固件主动 relink；一次窗口未出现某日志不足以排除该路径。已确认的边沿来自接收/处理链路变化的函数，不等于已经确认 0x80017134 是掉线原因。尚未向 PHY 或 MDIO 控制器写值。

`20261020T003626Z-cli.json` 的短时观察未得到可用 POA 或 relink 日志，仅收到 23 字节；不能用此排除主动 PHY 重连路径。

用户随后报告长 ping 192.168.1.4 经常丢包。将其记录为用户观测，不与采集端此前三次 ICMP 全失败混用。`20261020T003748Z-user-ping.json` 在 en0 上限时旁观 18 秒，只过滤目标 .4 的 echo request/reply，未捕获任何对应 ICMP。此结果不能证明用户没有发包或没有丢包；探测设备和实际接口尚待确认，也不能据此计算用户 ping 丢包率。

同期 `20261020T003745Z-cli.json` 收到两份有效 POA，均为 0x83818301，端口 0 up。结合先前真实 down 边沿，支持链路间歇变化，但不能把用户每一次 ping 丢失归因于已观测的那个边沿；点采样无法排除样本之间的短暂掉线，也无法排除链路 up 时无线/转发层丢包。下一步需要用户 ping 来源及带超时的序号/时间记录，才能做有效时间对照。

### 本轮进一步发展为用户所述的完全丢包

用户随即报告现在完全丢包。现场未改配置、未重启。`20261020T003835Z-arp.json` 中 AP HTTP 200，X99 两次 TCP/80 连接超时；抓取窗口无匹配 ARP，不能将其说成已经观察到 unanswered ARP。`20261020T003845Z-cli.json` 收到两份有效 POA，均为 0x83818301，端口 0 up。

因此本次“完全不通”不能简单称为持续物理断链：当前观测是端口 link up、AP 管理可达、X99 TCP 不可达，同时用户长 ping 全丢。之前真实 link down 事件仍有效，但物理链路恢复不保证数据路径恢复。需要检查链路恢复后的转发/MAT/ARP 重建，也仍需区分 X99 对端状态和无线承载；不能直接认定为单一 MAT 缺陷。

离线检查 CLI 注册表只找到 root 的 os 及 OS 下 thread/mem/spi/reg 等，本轮没有发现可直接安全调用的 ping CLI 命令。固件包含 ping 实现/字符串，不代表终端导出了该命令；尚未执行 AP 本机到 X99 的 ping，不将上游端探测冒充该项测试。

### 用户新增：无操作恢复、开始播放又丢包

用户先报告没有操作而连接自行恢复，随后报告一开始播放丢包就出现。此为明确的负载相关线索，但尚未完成可重复的暂停/恢复对照，不能直接确认某具体音频协议、吞吐阈值或资源耗尽为根因。播放源与其网络连接尚待确认。

`20261020T004437Z-cli.json` 收到 POA=0x83818301（端口 0 up）；无线累计 Tx success=11404、fail=4487、Rx success=117145、CRC=39029；AMPDU Tx success=10799、fail=5652，驱动显示 PER=34.3%；RSSI=-25/-29/0，Rx out-of-resource=0。这是累计驱动统计，不是音频专属丢包率，不据此排除内核网络缓冲池耗尽。

同阶段 `20261020T004426Z-arp.json` 两次 X99 HTTP 以及 AP HTTP 均 200，短窗口没有匹配 ARP。说明采样时普通访问可达，不能否定用户另一台电脑的间歇 ping 丢包。

已请求用户保持长 ping、电源、网线与连接不变，仅暂停播放 30–60 秒，观察是否减轻；下一步再对照恢复播放。暂停播放不保证协议停止所有流量，观察结果仍需按实际流量与响应解释。当前没有新配置更改、重启、计数清零或 PHY 写入。

只读内存诊断两次没有取得可用数值：`20261020T004630Z-cli.json` 为 Unknown Command，直接入口 `20261020T004743Z-cli.json` 仅返回 Memory system 标题。因此当前没有可报告的剩余堆内存或网络缓冲池容量，不能据此认定或排除资源耗尽。所有进程均退出。

用户报告暂停播放后仍丢包。该结果不支持“暂停音频即立即恢复”的简单瞬时负载假设，但暂停不等于 AirPlay 会话关闭或所有音频相关流量消失，也不能证明是某个固件状态被锁住。`20261020T004957Z-arp.json` 中 AP/X99 HTTP 均可达，仍不据此否定另一台电脑的持续 ping 丢包。下一项可区分的对照是明确断开播放设备与 X99 的 AirPlay 连接，保持 X99 开机、AP 和网线不变、长 ping 继续，再观察；在用户执行前不声称会话已停止。

### 再次报告全丢包：完整 down/up 对及重复 down

用户要求依据完全丢包继续排查。`20261020T005204Z-cli.json` 在一次只读会话中收到 `link=00, change=01`，随后 `link=01, change=01`，再读 POA=0x83818301、POC0=0x10007f7f；明确观测端口 0 断开再恢复，端口禁用配置未关闭内部端口。`20261020T005146Z-arp.json` 的本机 AP/X99 HTTP 均成功；不能把这些短请求与另一台电脑 ping 的全丢区间视为严格同步，亦不可否定原始报告。

为进一步诊断仅被动读取 MDIO 控制器，`20261020T005309Z-cli.json` 得到 PCR0=0x33000004、PCR1=0x05e10000，随后 POA up，再收到一次端口 0 down。没有向控制器发出读/写事务，不能把这两个控制器值当作 PHY 0 当前控制/状态寄存器，更不能据此证明某个驱动函数当时执行。回读这些寄存器没有发现足以确定根因的单项配置异常。

离线事件追踪新增 `link-event-disassembly.txt`：链路边沿投递事件 0x20，进入 0x8000494c 的处理线程，0x80004c8c 分支有计数与延后再次投递逻辑。它帮助定位掉线后的软件恢复链，但本身不是 PHY down/up 的已确认触发源。
