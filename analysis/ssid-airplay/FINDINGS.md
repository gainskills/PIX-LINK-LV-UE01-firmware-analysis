# 扩展 SSID 与 X99 同时冷启动问题

## 结论与验证边界

1. 扩展 SSID 的前端空值校验已确认；绕过这个校验不等于关闭扩展 AP。固件有隐藏 SSID、无线电总开关和 BSSID 数量三个不同控制点。`WLN_BssidNum=0` 是值得实测的独立关闭候选，但尚未上机验证，不能承诺无线回程仍可用。
2. 用户已澄清：当前不是故障现场。问题条件是 X99 以网线连接目标 AP、两台设备同时上电。因此当前在线响应和服务发现不能证明该冷启动问题已复现、已修复或不存在。

本次未写设备配置，未重启 AP 或 X99，也没有触发音频播放。

## 1. SSID 的实际控制逻辑

### 已确认

- 固件 `embedded-web/template-11.html` 的 `CheckValue()` 同时拒绝空的上游 SSID 和扩展 SSID。
- 同一提交函数强制 `c_bssid_num=1`、`c_WLN_ApCliEnable=1`，所以普通中继向导每次保存都会请求一个扩展 AP。
- `template-12.html` 的 `wlOnOff()` 控制 `c_radio_on`；其参数名称、配置映射和驱动调用链表示无线电控制，并非独立的扩展 SSID 开关。没有在设备上测试该开关对上游的具体影响。
- 驱动 `Set_SSID_Proc` 位于 `0x80042D50`。其长度检查接受 0–32 字节，将名称及长度写入 BSS 结构，并在相关状态下重启 AP 处理。没有发现“名称长度为零就独立停用扩展 AP”的分支。因此不能用空 SSID 代表关闭 AP。
- `HideSSID` 的处理函数位于 `0x80039190`，只改变 BSS 的隐藏标志并更新相关状态。隐藏名称不等于停止 AP 发射和禁止客户端连接。

### 参数与候选测试

| 功能 | 配置项 | ID | 结论 |
|---|---|---|---|
| AP 数量 | WLN_BssidNum | 0x04360100 / 70648064 | 当前网页回读为 1；0 是待验证候选 |
| 隐藏名称 | WLN_HideSSID | 0x04350200 / 70582784 | 与停用 AP 不同 |
| 无线总开关 | WLN_RadioOn | 0x04E70100 / 82247936 | 不适合作为保留无线回程的默认方案 |
| 上游客户端 | WLN_ApCliEnable | 0x04D40100 / 81002752 | 当前网页回读为 1 |

驱动配置解析 `0x8009CE74` 将 BssidNum 写入计数字段，只在超过硬件最大值时截断；该处没有把 0 强制改成 1。AP 启动代码 `0x8001BFA8` 读取这个计数并在为 0 时跳过对应的 BSS 处理。但系统仍会操作主接口 ra0，是否存在其他依赖必须动态验证。

`ssid-test-plan.json` 已记录仅修改一个参数的请求和恢复请求。二者均未发送。候选测试可能重启无线接口，且尚无经过验证的自动恢复方式；管理连接失联时可能需要物理恢复。不能把请求返回成功或参数回读为 0，单独当成扩展 BSSID 已停止发射的证据。

最终验证需同时满足：扩展 BSSID 停止广播/发射、上游连接仍在、以太网仍可转发；再检查重启后的持久性。这需要其他无线设备观察 BSSID，而非只看配置页上的名称。

## 2. X99 同时冷启动问题

### 当前只读观察

- RAOP 服务发现到 `SRS-X99 2FE512`，主机名 `Chromecast.local.`，当前 IPv4 为 `192.168.1.4`，服务端口 5000。
- 服务 TXT 记录含 `am=SRS-X99`、`tp=UDP`。这是服务公布的能力，不是对故障时实际音频包的抓包结论。
- 本机当前使用 en10，地址 `192.168.1.11`，本机网口协商为 100baseTX full-duplex。这个结果不能用于判断 X99 自身网口的协商状态，也不能单凭它确定物理连接路径。
- AP 和 X99 的 HTTP 页面均返回 200；一次观测的连接时间分别约 2.2 ms 和 4.4 ms。HTTP 可达不代表实时音频无丢包。
- 此工具环境对 AP、主路由和 X99 的 ICMP 测试全部超时，但同时间段 HTTP 可达、mDNS 可发现。ICMP、工具权限或本机过滤等因素尚未排除，不能把这些结果归为 X99 或 AP 的实际 100% 丢包，更不能当成冷启动 bug 的复现证据。

### 固件中找到的相关路径

- 无线客户端自动连接：`ApCliAutoConnectExec`、`ApCliLinkUp/Down`。
- MAC/IP 转换与学习：`MATEngineTxHandle/RxHandle`、`MATProto_ARP_Rx`、`MATProto_IP_Rx/Tx`、`IPMacTable_init`。
- DHCP 帧处理和单播/广播标志处理。
- IGMP snooping 和桥接组播过滤路径。固件内置默认 `WLN_IgmpSnEnable=0`、`WLN_MACRepeaterEn=0`；这些是镜像中的默认值，未确认设备运行时实际值。
- 以太网 PHY link-up/link-down 处理。

这些路径提供调查入口，并不证明其中存在导致 X99 丢包的缺陷。AirPlay 发现、音频传输和以太网链路应分别验证，不能仅因程序包含组播丢弃日志，就把音频卡顿归因于 IGMP。

### 最小对照实验

在保持上游、网线、端口、发送端和音源一致的条件下，分开进行：

| 实验 | 操作 | 主要用途 |
|---|---|---|
| A | AP 与通过网线连接的 X99 同时冷启动 | 复现用户报告的触发条件 |
| B | AP 先连通上游，再启动 X99 | 检查网络就绪时序是否必要 |
| C | A 出现故障后，只拔插 X99 网线 | 观察链路重协商/地址重新学习是否恢复 |
| D | A 出现故障后，只重启 X99 | 与 C 比较，区分客户端初始化和链路事件 |

每个实验分别记录：DHCP 获取地址的时间与结果、是否存在重复 IP/异常 ARP、mDNS 是否出现及消失、网口协商和错误计数、播放时的 UDP 时序/重传请求，以及在可正常使用 ICMP 的终端上的丢包结果。B 正常而 A 异常只支持启动顺序相关，仍不足以独自区分 DHCP、地址学习和 PHY 问题。

抓包最好位于中继上游和 X99 网线侧；普通交换机上的另一台电脑通常看不到 X99 的全部单播音频，不能将其抓不到包当成中继丢包。必要时使用交换机端口镜像或网络 TAP。应先确认实际接线，再决定抓包点。

Sony 的 X99 有线连接说明建议路由器先开启，再连接并开启音箱，并等待 LINK 指示稳定；这提供对照实验依据，不构成当前固件有 bug 的证明：[Sony 有线连接说明](https://helpguide.sony.net/speaker/srs-x99/v1/en/contents/TP0000634036.html)。Sony 的 AirPlay 排障还建议用直连路由器的有线连接进行比较：[Sony AirPlay 排障](https://helpguide.sony.net/speaker/srs-x99/v1/en/contents/TP0000634649.html)。
