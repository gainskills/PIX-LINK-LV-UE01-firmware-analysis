# 管理地址与 DHCP 功能

用户明确说明：DHCP 服务器是用户主动关闭的。后续保留关闭状态，不能把该状态当成固件自行关闭 DHCP 的证据。

## 已从固件确认

- DHCP 服务器开关配置 ID 为 `0x02020100`。`0x80149d48` 开始的函数读取该配置，仅当值为 1 时才进入其后续启动路径；反汇编见 `dhcp-server-enable-xrefs.txt`。
- LAN 管理地址模式使用另一个配置 ID `0x020a0100`（LAN_IP_MODE）。`0x80003664` 开始的函数读取它，零值进入 DHCP 客户端路径，并在 `0x800036d8` 调用 `DHCPC_init`；非零值进入静态 IP 路径，读取 LAN_IP、LAN_MSK、LAN_GW。该段模式选择没有读取 DHCP 服务器开关，见 `management-client-disassembly.txt`。
- HTTP socket 创建函数 `0x80010f54` 将绑定地址设置为零（INADDR_ANY）；没有在这里硬编码绑定 192.168.10.1。HTTP 服务仍要求设备实际拥有可达的本地 IP。
- 已提取的 LAN 设置网页没有提供 LAN_IP_MODE 控件。存在底层 DHCP 客户端能力，不等于目前中继模式已正确启用或能正确随上游重连恢复。

## 当前判断及边界

关闭本机 DHCP 服务器与从上游 DHCP 获取本机管理地址是两个独立配置入口。不能通过重新开启服务器来解决管理地址问题。192.168.10.1 的静态管理地址本身也不能证明该网段正在提供 DHCP。

尚未读取当前运行设备的 LAN_IP_MODE，尚未实测其零值模式在中继模式下的启动、租约获取和重连行为。因此当前不能声称管理地址故障已定位或修复，也不能把设备以前可达的 192.168.1.2 直接认定为 DHCP 租约。

后续实验先恢复直连管理入口并导出当前配置，再单独核对/测试管理地址客户端；保持 DHCP 服务器关闭，不与 HideSSID 测试同时改动。必须验证设备租约、管理页面、有线转发和冷启动恢复。

本次没有向设备提交配置或写入固件。Mac en10 当前仍为 192.168.1.11，未配置 192.168.10.2 临时别名。

## 中继默认 DHCP 开启与 X99 假设

用户进一步观察：中继模式下 DHCP 服务器默认也开启。固件中找到以下对应证据：

- 默认配置文本包含 `LAN_DHCPD_EN=1`、地址池 `192.168.10.100` 至 `192.168.10.200`、租期 86400 秒（`main-strings.txt` 的原始偏移 `0x19dc78` 起）。这些是固件默认值，不代表设备当前运行值。
- `embedded-web/template-11.html:282` 将 WlMode 设置为 1；同一 CheckValue 函数第 403 行的 `//setCfg('DHCPD_EN', '0'); //disable DHCP Server` 被注释。这条网页路径没有执行自动关闭 DHCP 的操作。单纯取消注释还不足以构成经验证修复：必须核对该字段是否注册、后端处理以及运行时停止服务。
- 启动调用点 `0x800047e0` 调用 DHCP 服务器启动函数 `0x80149d48`；紧邻的模式分支两条路径都到达这一调用点。启动函数本身检查服务器开关，开启才创建线程，并未在该函数内检查 WlMode。调用证据见 `dhcp-startup-callers.txt`，启动函数见 `dhcp-startup-disassembly.txt`。尚未完整验证线程内部是否另有抑制回应或隔离机制。

因此可以确认默认开关及网页切换路径存在可疑组合；尚不能确认中继模式下服务器实际向 X99 的网段发送了有效回应。

待证假设：两台设备同时启动时，上游无线尚未连通，而 AP 本地 DHCP 已可应答，X99 接受 192.168.10.x 租约；上游稍后恢复并不自动使已有租约变成 192.168.1.x。多个 DHCP OFFER 时客户端按自身策略选择，不能假定总是第一个回应获胜。也可能有错误 NAK/重试或中继转发时序问题，必须用包证据区分。

最小验证：保持用户已关闭的 DHCP 服务器状态，保持 BssidNum=1 及其余配置；同时冷启动 AP 与 X99，记录 X99 的地址、掩码、网关及 AirPlay 表现。抓包需在 X99 实际有线链路或镜像端口上，关注 UDP 67/68、X99 MAC、DHCP transaction ID、Server Identifier（Option 54）、OFFER/ACK/NAK、掩码和网关。Mac 替代 X99 的抓包只能验证通路或竞争存在，不能证明 X99 的选择行为；普通交换端口也可能看不到发给 X99 的单播回应。

判读：192.168.10.x 且租约来自 AP 支持错误服务器假设；169.254.x.x 表示未取得可用 DHCP 配置，不能单凭它断言双服务器竞争；正确 192.168.1.x/掩码/网关且仍故障，则 DHCP 假设不足以解释，需要继续查 ARP、转发和多播。关闭后多次冷启动正常会增强相关性，但单次成功不证明根因或永久修复。
