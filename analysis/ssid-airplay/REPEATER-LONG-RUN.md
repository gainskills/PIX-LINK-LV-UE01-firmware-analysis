# 中继模式：停用 192.168.10.x 管理地址与 DHCP 服务器

> 最新已验证配置见 [FINAL-TEST-CONFIG.md](FINAL-TEST-CONFIG.md)：LAN 静态地址清除、DHCP 服务器关闭、上游管理入口 http://192.168.1.2:8080/，已通过正常重启和有线转发验证。下文保留历史尝试及恢复过程。

用户要求长期运行测试：中继模式不启用 192.168.10.x 管理地址，不运行本机 DHCP 服务器，观察资源占用及 X99 稳定性。

## 测试配置

- 保持中继模式、现有无线 uplink 和 BssidNum=1。
- 本机 DHCP 服务器保持关闭：LAN_DHCPD_EN，配置 ID `0x02020100`，值 0。
- 首选使用已有 LAN DHCP 客户端模式：LAN_IP_MODE，配置 ID `0x020a0100`，值 0，让设备取得上游网段管理地址。
- 验证运行接口不再拥有 192.168.10.1；单纯旧地址无法访问不是充分证据。
- 保留通过新管理地址访问 HTTP 的能力；本轮没有请求关闭整个 HTTP/Telnet 服务。
- 不同时修改 HideSSID、无线数量、驱动或转发参数，便于解释长测结果。

管理地址的改变本身不代表减少了常驻服务或线程。停用 DHCP 服务器可能减少相关活动，但没有内存、线程和 CPU 对照数据前，不承诺节省资源或提高稳定性。

## 修改前与修改后验证

1. 恢复直连管理入口，导出设备当前配置，核对当前模式和 DHCP 开关，记录设备 MAC、上游租约及原始地址设置。
2. 确认固件现有设置支持上述行为，再使用配置修改。现有支持不足时才准备固件补丁；本文件不表示已有可刷写或经过验证的修补镜像。
3. 修改后在上游租约表或链路抓包确认设备的新地址，回读配置，并检查设备接口上的旧地址是否消失。
4. 检查 DHCP 服务器不再应答、无线 uplink、有线实际转发、新地址管理入口和一次冷启动后的持久化。
5. 再由用户接入 X99 进行长期运行及多次同时冷启动测试。记录 X99 地址/掩码/网关、AirPlay 中断时刻与恢复方式。

## 恢复边界

Mac 的 192.168.10.2 临时别名仅在 AP 仍拥有 192.168.10.1 时能提供管理入口。旧地址停用后，它不能保证找回设备。修改前必须完成备份并确认新地址发现方式；必要时使用已核实的设备恢复方式，不以未经验证的恢复流程作保障。

## 当前执行状态

用户配置临时地址后，Mac en10 为 192.168.1.11，同时拥有 192.168.10.2，旧管理入口可达。已导出当前配置（`longrun/before-profile.bin`，权限 0600，含私密设置，不应公开）。修改前确认为 SYS_WLMODE=1、LAN_DHCPD_EN=0、LAN_IP_MODE=1、LAN_IP=192.168.10.1、BssidNum=1、ApCliEnable=1。

已按用户授权提交原始表单 `CMD=LAN&GO=lan.htm&SET0=34210048=0&SET1=33685760=0`，收到 HTTP 200 成功进度页。旧管理地址随后不回应 ARP，HTTP/Telnet 也不可达。这里未能获得修改后的配置导出，不能仅凭进度页声称所有设置已正确持久保存。

抓包观察到 AP 相关 MAC `92:91:64:00:d1:39` 的 DHCP 事务，上游 Server Identifier 为 192.168.1.1，OFFER/ACK 地址为 192.168.1.2。对 192.168.1.2:80 的 SYN 收到 TCP RST，证明管理连接被设备一侧拒绝，不是单纯工具网络权限问题。尚不能证明该租约已正确配置到 LAN 管理接口；可能涉及 LAN/WAN 地址路径或服务恢复逻辑，不能把租约等同于可用管理入口。

修改前后强制通过 en10 的 Apple 连通性检测均为 HTTP 200，源地址为 192.168.1.11。修改前 OS 诊断的内存基线为 Total 3142 KiB / Free 1624 KiB / Largest 1619 KiB，线程列表无 DHCP 服务器线程、有 1 个 DHCPC 线程。修改后尚不能读取内存与线程，不能宣称资源占用下降。

受控冷启动尚未验证。已请求用户仅将 AP 断电重启，保留网线和临时别名；没有执行恢复出厂、刷写固件或改动 SSID。待重启后检查管理入口、旧地址、转发与配置持久化，再决定长期测试是否具备完整条件。证据见 `longrun/events.json`、`longrun/capture-summary.json`、`longrun/management-rejection.pcap`。

## 用户确认冷启动后的结果及恢复准备

用户确认重启后 192.168.1.2 仍不可访问。工具复查：旧 192.168.10.1 HTTP 超时；192.168.1.2 HTTP 80、HTTP 8080 和 Telnet 23 均连接失败；en10 仍为 192.168.1.11，实际有线转发检测 HTTP 200。通过 192.168.10.2 源地址访问 192.168.1.2 也未恢复管理。不能把这次隐藏 LAN DHCP 模式称为完整可用方案。

进一步静态证据：HTTP 创建监听函数 0x80010f54 在 bind(INADDR_ANY) 前调用 0x80114648，使用网络接口名作 SIOCGIFADDR（0xc0306921）查询；查询失败便返回 -1。HTTP 更新函数还比较缓存的 LAN IP 与 LAN 状态结构。这说明 INADDR_ANY 绑定不能保证缺失 LAN 地址或异常 LAN 状态时管理服务仍能启动。它是可能的故障路径，尚无当前设备接口/日志读回，不能据此确定唯一根因。

用户确认没有实体模式开关，并允许 Reset。已请求物理恢复出厂并等待完成。原始配置备份再次核对：4522 字节，SHA256 `d4b4a4663a6ebd403d7aecd81ad28a180ba943a10821c271426e43fafad4e98b`，#PROFILE / #VER_2_1，含原上游 SSID 和密钥，LAN_IP_MODE=1、LAN_IP=192.168.10.1、LAN_DHCPD_EN=0。

恢复请求已核对固件后端：POST setok.htm，multipart 字段 CMD=SYS_CONF、CCMD=3、GO=man_setting.htm，文件字段 **files**。后端 0x8000d894 查询 files，0x8000da20 提取文件并调用配置导入。网页 HTML 的文件字段为 binary，和后端不一致；不应凭 HTML 名称猜测上传请求。尚未实际执行恢复请求或声称导入成功。

下一轮先恢复备份并回读，后续考虑保持静态模式、把 LAN 管理地址移到主网段，避免依赖本次未正常工作的 LAN DHCP 路径。地址须先确认不与上游 DHCP 地址池/现有租约冲突，也不与 AP 自身上游地址冲突；已询问用户池范围或预留地址。在缺少这些信息时，不预设任意高位地址为安全空闲。
