# DMA 与链路的首次实机只读基线

本轮已登录原固件 AP `192.168.1.2`，仅发送固定白名单 `reg r` 命令。没有寄存器写入、MDIO 事务、配置导入、重启或刷写。采集连接及进程均已结束。

## 有效的正常可达窗口

UTC 2026-10-20 10:33:29–10:33:34，三轮顺序采样，共 30 个有效寄存器读数；每轮前后使用 curl GET `http://192.168.1.4/`。六次请求全部 HTTP 200，耗时 32–67ms。这只确认这些短请求可达，不证明播放或长期无丢包。

port 0 始终 up，CPU/DMA 收发索引均发生变化，未观察到贯穿该窗口的全局队列停滞。索引是环上的位置，减少可能来自回绕，不能把差值直接当成准确包数。各寄存器为顺序读取，CPU 与 DMA 索引并非同时快照，瞬时差值不作为损坏证据。中断状态读到 0 也不等于没有发生过中断。

原始采样：[20261020T103329Z-dma.json](dma-captures/20261020T103329Z-dma.json)。目录权限 0700、文件 0600，只有白名单读数、时间和探测状态，没有登录凭据或原始控制台正文。

## 已纠正的探测工具问题

首次沙箱内尝试没有登录响应，未执行寄存器查询。随后沙箱外的 `20261020T103037Z-dma.json` 已取得 30 个有效寄存器读数，但直接 Python socket 对 X99 返回 errno 65。一次本机 ARP 表检查也显示 incomplete；这不能独立证明 AP 内部转发故障。

进一步对照发现，两次 Python socket 都报 `No route to host`，紧接着 curl 均为 HTTP 200。故将首次记录中的 Python 连通性探测明确标为不可用于设备故障判断，保留原始读数，不删除失败记录。具体本机访问限制尚未定位，不把工具差异解释为 X99 自动恢复。见 [传输对照](dma-captures/probe-transport-comparison.json)。

`20261020T103201Z-arp.json` 的 AP、X99 HTTP 探测也均为 200，抓包未捕获目标 ARP，不据此认定未应答 ARP。最终采集工具已改用验证可用的 curl。

## 寄存器依据与采集边界

| 只读地址 | 用途及原代码依据 |
| --- | --- |
| 0xb0110080 | POA；原端口中断及 carrier 查询读取 |
| 0xb0100804 / 0808 / 080c | TX 环长度 / CPU / DMA 索引；初始化 0x80018318..0x8001832c，原 TX 诊断读取 0x80017914..0x80017928 等 |
| 0xb0100904 / 0908 / 090c | RX 环长度 / CPU / DMA 索引；初始化 0x80018330..0x80018354，原 RX 处理/诊断读取 0x80017494..0x800174a4、0x800177b4..0x800177d0 |
| 0xb0100a04 | 原初始化轮询的 PDMA 全局配置 |
| 0xb0100a20 | 原中断处理读取、随后另行写入确认的状态；本采集只读取 |
| 0xb0100a28 | 原驱动写入的中断使能掩码；本采集只读取 |

[capture_dma_state.py](../../logic/ssid-airplay/capture_dma_state.py) 最多三轮、查询阶段限时 30 秒，逐条校验响应地址和格式；缺失、重复、损坏读数不补零。`--self-test` 在不联网时通过一个合法样本及五个错误样本拒收检查。登录复用此前已验证的 nc 会话，退出时关闭连接。

这是可用于后续故障窗口对照的**正常基线**，尚未取得故障中的 DMA 状态。不得据此排除短暂卡死、丢中断、特定流量转发错误或已经观测过的物理 link down。
