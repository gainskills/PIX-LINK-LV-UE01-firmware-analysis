# 新旧固件尺寸与 Flash 容量复核

范围：仅检查本地原始导出、日志、固件及候选；没有访问 AP 或执行任何设备命令。

| 项目 | 原固件 | 新候选 | 变化 |
| --- | ---: | ---: | ---: |
| uImage 文件 | 718108 | 718108 | 0 |
| uImage 载荷（不含 64 字节头） | 718044 | 718044 | 0 |
| 载荷中的加载器前缀 | 9280 | 9280 | 字节完全相同 |
| LZMA 压缩流（含流头） | 708764 | 655421 | -53343（约 7.53%） |
| 压缩流后的填充 | 0 | 53343 | 新增 0xFF 填充 |
| 解压主程序 | 2174360 | 2174360 | 0 |

所有尺寸单位为字节。减少的是压缩流占用，不是升级文件长度或解压程序内存。当前候选约有 52.09 KiB 压缩区域余量；运行时堆栈、连接缓冲等内存占用未验证。

## 已确认的映像布局

原 uImage 与已导出 Flash 中 0x50000 起的字节完全一致。新旧容器若写入相同起点，都覆盖 `[0x50000, 0xFF51C)`，长度 0xAF51C；不会因新候选尺寸增加而向后延伸。

| 区间 | 可确认内容 |
| --- | --- |
| `[0, 0x50000)` | 主程序容器之前的数据，含 U-Boot；完整子分区边界尚未恢复 |
| `[0x50000, 0xFF51C)` | 当前已校验的原 uImage；新候选同长 |
| `[0xFF51C, 0x100000)` | 本次读取范围内、容器之后的 2788 字节；不能当作可用分区空间 |

uImage 加载和入口地址均为 0x80500000。新旧头部仅 CRC 字段不同，其余字段保持一致。两者头部和载荷 CRC 都通过，LZMA 流均正常结束并解压为相同长度。新候选的非目标字节与资源/加载器完整性另由 verify.py 校验。

## 容量结论

**尚不能确认物理 Flash 容量。** `metadata.json` 的 flash_bytes=1048576 是读取文件长度；原 REPORT.md 也明确记录只读取前 1 MiB。read_flash.py 按调用者给定的 size 读取，没有探测芯片容量，因此该长度不能作为芯片容量或完整备份的证明。

固件/Bootloader 含多种 SPI Flash 型号表，例如 MX25L1605D、MX25L3205D、W25Q32BV、GD25Q32B 等；它们是编译支持列表，不是本机选中的型号。现有日志未找到实际输出的 manufacturer/device ID。不能凭列表、文件长度、末尾填充值或可读地址推断物理容量。

## 恢复与进一步验证入口

导出区内存在 U-Boot 1.1.3（2016-08-07）的 `spi id` 帮助、SPI ID 识别信息和 TFTP 加载/写入菜单，说明恢复相关代码存在；不代表已验证这块板的串口接入、启动菜单、TFTP 参数或恢复成功。

eCos 运行时已知 `spi` 命令只显示 rd/wr/er；不能把 Bootloader 的 `spi id` 直接当作运行时可用命令。后续可通过实际芯片丝印、已有启动串口日志，或在经确认的 Bootloader 控制台执行只读 ID 查询获得型号/JEDEC ID，再核对容量和擦除粒度。完整备份应在容量确认后覆盖整个芯片，并保留配置、MAC/校准区。

本轮没有为了读取 ID 重启设备、访问 Bootloader 或测试恢复，也没有制造可直接刷写的包。

精确字段与 SHA256 见 size-capacity-evidence.json。

## PCB 照片更新（2026-10-20）

用户提供的本机 PCB 照片确认板号 LV-UE01-V1.0、主芯片 MT7628KN，并可辨认 Zetta ZD25Q16 系列 Flash。据型号可确定标称容量为 16 Mbit（2 MiB）；本机 JEDEC ID 尚未读取。此前“物理容量未知”是照片提供前的结论。1 MiB 导出文件只覆盖该标称容量的一半，不能称为完整备份。此结论没有改变候选镜像的尺寸、写入范围或分区边界。详情见 ../ssid-airplay/PCB-COLD-START-REVIEW.md。
