# 诊断区在早期启动中的保留验证

本轮延续原生 loader 验证后的准备项：检查 main 进入构造函数阶段以前，原生初始化是否覆盖新增诊断。只使用本地模拟内存，没有访问 AP、重建或修改候选镜像。

## 三组原指令实验

| 场景 | 结果 |
| --- | --- |
| 原版对照，从 0x80000400 进入 | 到达 0x80160218；BSS 清零，界外保护字节保留 |
| 原基线诊断候选，同一路径 | 到达相同位置；四个诊断范围全部保持，main 除模拟 HAL 替身外逐字节不变 |
| 仅模拟内存中的 BSS 内哨兵 | 原清零函数确实清除了哨兵，验证实验能发现放错区域的情况 |

实验先用非零字节填充模拟 RAM，再加载 main；因此 BSS 全零不是模拟器初始内存为零造成的假象。原清零函数 `0x80000b28` 使用范围 `0x80213198..0x80264518`（右端不包含），起点恰好位于 main 已加载内容之后。

实际诊断负载/计数位于 `0x8019f0c2..0x8019f540` 分配区，CLI 回调位于 `0x802123f0`，均在这个清零范围之前。四个许可修改范围分别作了启动前后完整比较；同时比较整个 main，避免只检查几个哨兵却漏掉其他写入。

**结论仅限早期启动：在已执行的这段路径中，诊断代码、回调及计数区没有被覆盖。**

## 执行与替身边界

原入口、CP0/cache 初始化、异常向量设置、原生 BSS 清零等指令在模拟器中执行。板级初始化函数 `0x801606e0` 仅在模拟 RAM 中替换为返回指令，以避免把实际外设条件虚构为已验证。整个 main 的期望比较明确扣除了这 8 字节模拟替身；候选文件没有这种改动。

运行在 `0x80160218` 构造函数分发入口停止。该函数原生从 0x80212d7c 向 0x80212d28 遍历 22 个指针；本轮静态核对原版/候选这段表逐字节一致，但**没有执行这些构造函数**。不能由此排除后续构造、分配器、设备初始化或网络运行时对内存的影响。

真实缓存一致性、DRAM 容量/别名、板级外设状态、完整启动、实际诊断命令和恢复均不在本实验结论内。
