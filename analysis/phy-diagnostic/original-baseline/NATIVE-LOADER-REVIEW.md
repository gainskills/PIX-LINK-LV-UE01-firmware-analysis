# 原生自解压启动代码验证

本轮补充的是固件准备验证：在本地 Unicorn 的合成 RAM 中，从 uImage 的原生自解压入口执行到 main 入口。没有访问 AP、重建或刷写镜像，没有执行 main 内的设备/网络初始化。

## 与此前校验的区别

此前独立验证器使用 Python LZMA 校验压缩数据。本实验直接执行原固件镜像内的 MIPS loader 和 LZMA 解码指令，不用 Python 解压结果填充模拟 RAM；预期 main 仅用于结束后的逐字节比较。

原版与候选的 loader 前缀逐字节相同。每次仅将容器头之后的 payload 放入模拟地址 0x80500000，从这个入口运行，在 0x80000400 停止。主固件没有继续执行。

## 三组结果

| 输入 | 原生代码结果 | 输出核对 |
| --- | --- | --- |
| 原版对照 | 到达 0x80000400 | 全部 2,174,360 字节与原 main 一致 |
| 原基线诊断候选 | 到达 0x80000400 | 全部 2,174,360 字节与诊断 main 一致 |
| 模拟内存中的无效 LZMA 属性 | 进入 0x805002b8 失败分支 | 没有到达 main 入口 |

原版和诊断候选均进入原缓存处理例程一次，模拟 UART 写出 `ZzOK` 及换行。无效属性场景没有进入缓存例程。UART、RAM、CP0/cache 均由模拟器处理，这不是实际串口启动日志或缓存一致性证明。

无效属性仅修改该次模拟 RAM，不输出或修改固件文件；U-Boot 的容器 CRC 检查不在该负例范围。此前独立制品校验仍负责容器头/数据 CRC 和压缩边界。

对照用时约 8.8 秒、候选约 11.4 秒是本机模拟器执行时间，不能用作设备启动速度或候选性能比较。

## 来源与制品保持不变

- 原版 uImage SHA256：`43ef36588e9f3c08b302583a60fc30bcb8fd374953a82a88eb64fcef2714c243`。
- 候选 uImage SHA256：`64421c4fada9034e9622b0a839745a758534dc75d77ad79dd6da9b71bdbf3706`。
- 候选 main SHA256：`0ccb104d36fe70b0c5411979eda687519c0395642efb6ff22a168b40ec5251fe`。

脚本固定验证上述输入指纹，原版对照失败时不继续用该环境判断候选。每个场景有 20 秒模拟执行上限和 2.5 亿条指令上限，进程已正常退出。

证据：[native-loader-experiment.json](native-loader-experiment.json)。复现：`python3 firmware-analysis/ap-192.168.1.2/phy-diagnostic/emulate_native_loader.py`。Unicorn 在当前 macOS 需要沙箱外初始化，但该脚本不使用网络或设备。

## 未验证项

实际 DRAM 容量/别名、启动前硬件状态、U-Boot 加载、真实缓存一致性、main 的完整启动、诊断区在实机执行、真实 MDIO 时序及恢复入口仍未验证。模拟器映射的 8 MiB RAM 仅是实验模型，不是容量测量。

结论仅为：**当前候选压缩数据可被镜像中未改动的原生 loader 正确展开**。候选继续为 NOT-FOR-FLASHING，尚不是 X99 掉线修复或经过实机启动验证的发布版本。
