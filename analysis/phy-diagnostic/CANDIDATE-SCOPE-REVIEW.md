# 诊断候选的基线与隔离范围复核

结论：此前生成的诊断镜像是“网页更新 + 默认值调整 + PHY 诊断”的组合，不是相对运行中原固件的纯诊断镜像。现有二进制保留原哈希，本轮没有构建或应用新镜像。

## 独立核对结果

| 比较 | 实际改变的字节 |
| --- | ---: |
| 原固件 → 网页候选 | 152,822 |
| 网页候选 → 诊断组合镜像 | 496 |
| 原固件 → 诊断组合镜像 | 152,845 |

网页清单声明 46 个范围，覆盖 160,360 字节；网页差异均在其中。诊断相对网页基线的差异均在三个诊断范围。整个组合镜像相对原固件的差异在二者并集内；没有额外越界修改。三个数字是不同基线的逐字节比较，不可直接相加。

8 个明确定位的原生 MDIO 读/写、PHY 初始化、主动重连入口之后代码、硬件链路中断、上游处理/监控范围保持原字节；relink 入口新增跳转另行列出。loader、容器尺寸、头部/载荷 CRC 及 LZMA 回读通过。不能由此扩大推断整个镜像行为与原固件完全相同。

## 继承的非诊断变化

- WPS 出厂默认从 7 改为 0（main 0x19e1a5）。它是默认配置变化，不证明已保存的实机 WPS 状态改变。
- 清空 18 个图片资源及其响应长度。
- 替换 index/LAN/dashboard/login 内容和 HTTP 回调。
- 用新管理控制器替代 jQuery，重命名脚本资源并调整响应长度。

没有发现声明范围以外的原生 PHY、无线驱动、内核或 DHCP 实现修改。新页面初次加载为配置/状态 GET，没有自动 POST、扫描或重启。但明确点击保存后，新控制器会提交模式、SSID/安全、带宽/功率等字段，普通保存还会强制 LAN_IP_MODE=1、SYS_RM_EN=1，并在中继模式关闭 DHCP server；这些界面行为可能影响后续对照。因此不能将使用组合候选后的结果直接归因于诊断增量。

## 更小基线的设计可行性

已在内存中验证一个隔离布局：从原 main 开始，仅将 favicon 分配区 0x19ecc2..0x19f140（1,150 字节）清空，放入现有 780 字节诊断负载，将原 favicon 响应长度指令改为 0，再修改 relink 入口和 reg 回调。其他原页面、默认值、资源、native 代码保持原字节。

该模型相对原 main 仅改变 1,064 字节；原 WPS 默认保留。没有输出固件镜像，仅输出可复现的布局/压缩指标。独立审查在内存中复现了 nice_len=128 的结果。

| nice_len | 压缩字节 | 预算余量 |
| --- | ---: | ---: |
| 128 | 708,646 | 118 |
| 273 | 708,779 | -15，不可用 |
| 64 | 708,598 | 166 |

三组均校验原 LZMA 属性和完整解压回读；其中一组超过预算，必须拒绝。可用模型仍只有很小余量，尺寸可装入不证明资源区可执行、缓存正确、MDIO 时序、候选能启动或恢复有效。原 favicon 区将不再返回浏览器图标；这项资源变化必须纳入诊断范围。

审查后续已将隔离设计实现为 builder.py --baseline original，独立制品见 original-baseline/README.md。此处的内存可行性实验仍保留为设计阶段记录；新制品虽已生成和离线验证，仍未启动或刷写，启动/恢复入口限制不变。
