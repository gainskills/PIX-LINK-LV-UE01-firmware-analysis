# 手动 RAM 加载候选流程与下一项决策

当前原固件与诊断候选均未进行新的实机操作。下一项实际进展需要建立可控串口入口；现有离线结果不足以批准刷写。本文件是分阶段验证方案，不是可直接照抄的设备命令。

## 已补齐的原始命令实验

[emulate_manual_tftp.py](../../logic/recovery/emulate_manual_tftp.py) 从原命令入口 0xbc00c020 执行至返回；使用同一份已验证启动区。环境查询、网络循环、缓存、环境保存和 bootm 后端均采用模型或拦截。没有下载实际文件，没有执行真实 bootm。

18 组组合：autostart 缺失/no/yes × 参数更改标志 0/1 × 网络返回 -1/0/718108。

| 模型输入 | 原命令观察结果 |
| --- | --- |
| 网络返回 -1 | 命令返回 1，不调用 bootm 或环境保存 |
| 网络返回 0 | 命令返回 0，不调用 bootm 或环境保存 |
| 正长度，autostart 缺失或 no | 命令返回 0，不调用 bootm 或环境保存；标志 0/1 均如此 |
| 正长度，autostart=yes，标志 0 | 调用 bootm，不保存环境 |
| 正长度，autostart=yes，标志 1 | 先保存环境，再调用 bootm |

以上均恢复命令入口的栈指针；没有到达直接固件写入/擦除入口。结果见 [manual-tftp-experiment.json](manual-tftp-experiment.json)。零长度也能返回成功，因此未来必须独立检查实际长度和镜像内容，不能只看命令返回值。

原命令在 0xbc00c34c 查询 autostart，0xbc00c364..0xbc00c390 执行字符串比较；只有匹配 yes 才进入 0xbc00c398 的自动启动路径。具体原指令见 [TFTP 反汇编](ram-tftp-handler-disassembly.txt)。本实验只验证命令本身，不验证菜单调用者、环境编辑器、控制台提示符、网络传输或其他动态路径。

复现：

```sh
python3 firmware-analysis/ap-192.168.1.2/recovery/emulate_manual_tftp.py
```

本机 Unicorn 需在沙箱外初始化，脚本只访问本地文件。

## 分阶段推进

1. **串口识别和启动日志。** 需能确认逻辑电平的 USB 串口接口及测量条件。先确定焊盘地线、电平和设备 TX，采集启动输出；针序和电平目前未知，不能凭照片连接。设备继续独立供电，不接适配器 VCC。此阶段不发送命令或刷写。为取得完整开机日志可能需要一次受控重启，应先安排测试窗口。
2. **确认可中断启动并进入命令行。** 在第一阶段证据具备后，单独确认输入方式与菜单行为；不采用已发现会擦写的 GPIO Upgrade 路径。仅列出命令与当前环境，核对 autostart、地址、内存布局。现有编译默认波特率不是实机测量值。
3. **验证手动传输能返回。** 在确认环境编辑仅作用于 RAM、手动命令及内存范围之后，再考虑关闭自动启动并手动传输原镜像。先验证原镜像，不直接加载候选。不得调用 saveenv 或菜单自动流程；传输后检查长度、内容与返回控制台。具体地址和命令在实机信息明确后生成，不沿用实验中的合成地址。
4. **受控 RAM 启动。** 仅在前述步骤及恢复控制具备后，另行确认原镜像 RAM 启动，再考虑诊断候选。RAM 启动仍会影响当前网络服务，且启动应用可能自行写配置；不承诺整个过程没有 Flash 副作用。先前原生 loader 实验不能替代这一阶段。
5. **故障取证。** 候选实际启动并验证状态恢复后，才使用 reg phy。保留原始记录、两次 BMSR 和失败前缀，按 [输出验收](../phy-diagnostic/original-baseline/OUTPUT-ACCEPTANCE.md) 执行。刷写持久化并非以上步骤的自动后续动作。

## 为什么现在需要用户决定

用户此前明确没有串口适配器和万用表，不将其当作现有条件。已检查运行时 CLI 的 mem/reg 与启动控制台注册路径，目前没有验证出可替代串口的软件加载或菜单控制入口。继续增加 MMIO 模型不能验证真实启动与恢复。

需要决定是否准备串口测量条件、进入第一阶段。若暂不准备，保留原固件；现有故障窗口采集工具可在用户报告故障时使用。不会用反复正常轮询替代故障证据，也不因已有备份而直接刷写。
