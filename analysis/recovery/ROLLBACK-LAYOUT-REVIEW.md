# 备份、镜像范围与回滚演算

使用现有双份 2 MiB 备份、原 uImage 和原基线诊断候选完成内存字节演算。两份备份逐字节一致，原版/候选 uImage 头部与载荷 CRC 均通过；没有访问 AP、执行 Flash 后端或生成整片刷写文件。

| 项目 | 离线结果 |
| --- | --- |
| 固件容器范围，右端不含 | 0x50000..0xff51c，718,108 字节 |
| 假设 4 KiB 对齐 | 覆盖 0x50000..0x100000，共 176 块 |
| 假设 64 KiB 对齐 | 同一覆盖范围，共 11 块 |
| 对齐范围超出镜像的尾部 | 2,788 字节，当前备份中全为 FF |
| 仅替换候选的内存模型 | 镜像范围外逐字节不变 |
| 将覆盖范围恢复为备份内容 | 整片逐字节恢复，SHA256 与原备份一致 |

4 KiB / 64 KiB 只是两个对齐假设，没有测量芯片实际擦除粒度。尾部全为 FF 是这份历史备份的内容，不构成允许忽略未来尾部数据的规则。

## 不能只靠原固件文件回滚所有副作用

已定位的 GPIO Upgrade 调用者还会请求擦除 0x30000..0x40000，位于 uImage 范围外，见 [启动路径](BOOT-ENTRY-REVIEW.md)。演算将该范围填 FF，再仅恢复原固件覆盖范围：整片仍有 6,506 字节与备份不同。继续恢复备份中的环境区后，才重新逐字节一致。

这证明“恢复原 uImage”和“恢复备份状态”有不同范围要求；并不证明真实擦除成功，也不提供操作步骤。历史环境恢复还可能撤销备份之后的配置。无线校准数据的位置未由本实验确认，不能把环境区擦除直接称为校准区损坏。

## 压缩差异与修改范围

原版和候选 uImage 有 705,872 字节不同。这是重新压缩后的容器比较；解压 main 的改动仍为既有四个许可范围、1,064 字节。不可按 main 的小范围修改去推断 Flash 只需改写相同数量的字节。

## 证据与边界

脚本 [analyze_rollback_layout.py](../../logic/recovery/analyze_rollback_layout.py)，结果 [rollback-layout-evidence.json](rollback-layout-evidence.json)。复现：

```sh
python3 firmware-analysis/ap-192.168.1.2/recovery/analyze_rollback_layout.py
```

只读取本地备份/镜像，输出不含配置原文、凭据或 MAC。恢复后的内存 SHA256 为 b3413627600d69787c731355827d633bee30407062886df0fc7489d6aa704f9a，与已验证备份一致。

演算不模拟断电、部分写入、Flash 时序或实际启动。控制台入口、JEDEC、擦除粒度、实机恢复及候选启动仍未验证；候选保持 NOT-FOR-FLASHING。现有条件下不再通过增加模型把这些硬件缺口判为通过。
